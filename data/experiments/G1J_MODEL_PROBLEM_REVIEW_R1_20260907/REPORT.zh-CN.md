轮次：`G1J_MODEL_PROBLEM_REVIEW_R1_20260907`。日期：2026-09-07。环境：WSL `UbuntuRecovered`。

## Agent 级结果与本轮范围

本轮仅整理证据，没有新增 Agent 运行：Strict、completed、mutation 和终止原因均无新增测量。历史 R2 A 为 **Strict 0/12、completed 0/12、mutation 0，12 题均为 strong_planner_unavailable**；其中 11 题没有 RWKV generation，不能把这组分数当作 G1J 模型能力，也不能拿来与 G1i 相减。当前仍无合格的同代码项目开发集双零基线。[E01]

## 主要判断

**G1J 已暴露出合同保持、任务进度使用、证据解释与推理收束方面的模型行为缺陷。工程接入修好后，这些缺陷仍然存在。** 这与“已经证明 G1J 权重或 RWKV 架构先天不行”是两个不同结论：目前样本和对照不足以分离基础权重、提示组织、采样、思考模板、初始 State 等因素。

当前已能排除部分充分解释：最新 Planner 在 HTTP 200、自然 stop、完整 JSON、8,192-token 输出预算下依然失败；历史 Executor 在重复披露已消除、remaining target 明确的输入下依然读回旧目标；小 Stage Checker 在输入远低于窗口时重复到输出耗尽。[E02–E06、H01–H03]

### 1. 合同失败发生在模型正常生成之后

最新 Planner 请求的 system prompt 明确列出了五个顶层字段、义务绑定、phase 对应的 root 规则，以及 success_evidence 数组示例。模型在 1,918 输入、4,651 输出 tokens 下自然结束，JSON 语法成立；生产首先因额外 goal_digest 拒绝，其他字段与语义问题来自另行只读观察，不能写成 parser 已逐项报错。[E02–E03、E10]

前一份完整输出是 7 阶段/19 步，其字符串、同阶段依赖、写入冲突等问题仍有参考价值，但当时的提示和解析边界不同。两次失败可说明同类现象曾重复出现，不能算作受控修复前后比较；取消数量上限也不会自动消除关系错误。[E04]

最新计划还暴露需求覆盖风险，例如并发义务 O3 尚未被当前步骤绑定。但滚动计划允许后续增加步骤，尚未执行到完成边界，不能直接宣称整个任务最终漏做。需要考察完整义务—步骤—动作—证据链，而非只检验 JSON。[E02]

### 2. 已知事实没有稳定改变模型行为

历史 R5 使用真实 Controller、存储、Harness 和 zero-State 13.3B，固定 Planner step 与诊断 Selector，隔离 Executor 状态传递。第二次输入明确记载 completed 与 remaining，且旧三种重复副本已经不存在，模型仍重复旧路径。这是比“Agent 没完成”更具体的残差证据：需要使用的进度已经到达，但输出没有遵循它。[H01–H02]

它只能支持该历史输入下的模型行为缺陷，不能直接推出“WKV 记忆容量不够”。同样，旧 E5 报告关于“短输入已解决历史动作竞争”的结论必须结合后续 R5 失败理解，不能停留在短矩阵 33/42 或读取 18/18。[H02–H04]

最新小 Stage Checker 的原始生成反复混用不同对象的 SHA，并在 revision 问题上重复，最终没有任何有效判定。这里可记录证据解释未收束，不把模型思考中的断言当作真实文件状态，也不把 mock accepted audit 当作真实审计能力真值。[E05–E06]

### 3. 输出预算、输入容量与终止能力要分别看

小 Stage Checker 输入加实际输出共 3,405 tokens，远低于服务 16,384 窗口；直接失败是重复生成直到 2,400 输出预算耗尽。仅扩大预算可能延长重复，能否改善尚无受控证据。open_think、temperature 0.1、零 presence/frequency penalty 等都属于本次配置，不能跳过对照直接把问题定位到权重内部。[E05、E11]

19 步 fixture 的 15,067 输入加登记的 2,400 输出预算为 17,467，已超过窗口，因此没有生成。这是当前服务与完整阶段输入的容量约束，不能说成模型“看不懂 19 步”或“长 State 失忆”。固定步数限制不能代替解决实际容量问题，删除证据或把资源耗尽记为完成也不能证明能力改善。[E07]

### 4. State 和记忆来源要对应实际调用

当前源码明确 Executor 的 State 范围为一次已选动作，新动作不继承前一次工具 WKV；它依赖 ledger 的事实投影。Selector 三次菜单求值相互独立；Planner/Stage Checker 显式 zero。不同角色独立从自己的初态开始。这种隔离有避免动作和角色污染的目的，但它没有提供“同一 recurrent State 跨完整项目持续积累任务理解”的实验证据。[E11–E13]

应区分初始 StateTune、单次调用内递推、跨动作/角色的事实传递三个对象。不能把数据库留存、State handle 存在、角色局部分数或 fresh-State 多菜单投票直接解释成长程记忆增益。反过来，只有在模型实际获得关键事实之后仍失败，才有理由把该次残差进一步归因于模型使用信息的能力。[E08、H02]

### 5. 数据问题也是模型学习与泛化问题

当前共享 builder 已统一，但生产 trace 抽取器尚未实现。最后一次 input.prompt 可能仅是 delta；只训练这段文本会漏掉实际 bootstrap、初始 State、rollover/fork 和 token/stop 历史。即使字段名完全相同，也不能视为相同学习条件。[E08–E09]

历史短事实成功、完整事实失败说明至少有输入分布迁移风险；不应把局部高分当作已经学会通用任务状态。当前尚无证据证明某个非零 State 在现行生产协议下解除首错并提高 Agent Strict。训练轮次与授权另有约束，不能把“再训一轮”写成现成结论。[E09、E14]

## 与 G1i 的比较边界

两代模型应分别比较 13.3B 与 13.3B、2.9B 与 2.9B；zero、StateTune 和外置 Head 的结果不可混算。还应固定题目、输入、工具菜单、事实投影、采样、token/stop 边界、评分与执行框架。历史 G1i 系统成绩与当前 G1J 探针使用不同条件，不能用分数相减得出基础模型升级幅度。

已找到 2026-09-01 的逐样本配对审计：同一 S60/V7 dev 的 **2,571 条**，两代都为 2.9B、zero State，使用相同 h64 Head 配方，但 Head 分别在各自基座 Hidden 上训练。样本身份、label、split、kind、language、position 对齐，selected 等于 raw argmax，没有后处理。这是**基座＋匹配 Head 组合**的直接比较，是既有冻结结果的事后审计，不是本轮新预注册实验，也不是当前无 Head Selector 的成绩。[H05]

**已观察到的强项是局部修复，而非某大类能力全面提升。** G1J 修复 10 条，包括把错误的 run_command 改为 check_command；把错误的 date_diff/current_time/file_digest 等改为 read_file；把错误的 read_file 改为 write_json 等。S39 内也修复了 6 条，但新增 22 条错误，所以该分片总体仍下降。S28 与 S55 各净增 1 条，样本增量不足以宣称相应能力显著提升。[H05]

**已观察到的弱项是多步骤上下文中的当前动作辨别。** 29 条新增错误中，22 条出现在 S39。典型新增错向包括 make_directory→append_file、read_file→write_json、write_json→write_file，也有 check_command→run_command、read_file→search_text、final_answer→其他工具。它们都是选中了错误的真实操作，不能解释为 JSON、HTTP 或 parser 故障。中文有修复 3/回归 8，英文有修复 7/回归 21，因此不能缩成单一语言问题。[H05]

两代共同错 29 条，另有 2,503 条共同正确。配对结果只证明上述输入与 Head 条件下的差异：原报告还指出完整 Goal 与当前 frontier 的位置竞争。输入组织与 Head 训练都会影响分数，无法单独确定基础权重的贡献，更不能将旧 Head 方案恢复成当前修复建议。表中名称说明数据来源分片，不代表五种独立隔离的智力能力；S55 的历史目录名含 true，不据此将其称为真实用户 trace。[H05–H06]

**13.3B 的强弱目前未知。** 同一历史审计明确缺少 G1i 在相同 role-pure prompt、zero State、stop suffix 下的配对 raw trace。G1J 的 Executor 1/1、Auditor 2/2 只是极小角色探针；旧 G1i Ladder 0/3 混入旧 State、旧图与旧审计链，不能比较。近期 G1J 的计划、进度和推理终止失败成立，但没有同条件 G1i 结果，不能叫作“相对 G1i 的新增退化”；输出更长、有思考文本也不是推理变强的证据。[E02–E06、H05]

因此，对用户问题的可核验回答是：**2.9B 的历史匹配 Head 组合有少量局部改善，但总体工具选择及多步骤当前动作选择下降；13.3B 的规划、代码、证据审计、推理与长程能力尚不能给出代际胜负。** 当前无 Head Selector、当前 State 组合和完整 Agent 也没有可用于此结论的两代同条件对照。

## 问题之间的放大链与后续判断标准

计划关系错误会改变 Controller 的 eligible operations 与目标范围；Executor 的目标/身份错误会阻断 Harness 或制造无进展动作；Auditor 若不能区分证据对象或及时结束，又会阻断阶段推进。角色各自能生成文本，不代表这条链条能完成用户目标。不能用外置 Head、额外修补调用或用例规则代替模型完成它的职责。

后续应沿既有规范执行：先使当前 Goal 角色稳定交付合法计划与阶段判定，再冻结完整 12 题双零；按 Planner→Selector→Executor→Harness→Auditor 的首错与放大链归因。对模型残差做同输入、只换一个角色 State 的反事实，只有解除首错且 Agent 增益超过实际双零噪声才支持该 State 有效。两代比较需要独立冻结，当前整理本身不启动新评测或训练。

工程验证继续用于保证输入真实完整、State 身份正确、工具与验证器可信；模型验证则必须回答：能否忠实使用进度、选择合法参数、保持计划关系、解释真实证据并自然结束。两者都要通过。没有完成全部同类场景、边界、完整流程和 Agent 回归前，不把上述问题标为解决。
