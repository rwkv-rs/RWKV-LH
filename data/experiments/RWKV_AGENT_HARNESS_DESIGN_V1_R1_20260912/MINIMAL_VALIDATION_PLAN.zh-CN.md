复用R5四份短文件及其原工作区：RP-API-01 README.md/server.py/verify_public.py，RP-API-02 README.md。原R4/R5完整清单继续作为来源身份；禁止新建datasets版本或修改旧评分。

最终登记必须明确哪些“重要覆盖项”缺失会构成实质遗漏，哪些只是完整程度差异；不能运行后凭印象改变严重性。每项独立标覆盖/部分/遗漏，不能把一组全有全无当唯一指标。

整体尺度拟定为：满足（主要含义充分且忠实）、部分满足（主旨基本正确但有影响理解的重要遗漏或局部无依据内容）、不满足（主旨/关键功能实质错误或严重误导）、无结果。分别报告事实忠实性与遗漏，不把一处局部问题抹成所有信息都错。具体实例与稳定门须在REGISTRATION冻结，不用旧答案作为完整参考范文。

语义评审看原任务、原文件与原样最终结果，不看工具路径、调用次数或臂标签；匿名映射在外部保存。允许转述，不逐字匹配。评审逐判断给出证据，分歧不能通过“模型重答一次”消除；若双评审可用，冻结其分歧处理规则与身份，若只有单一评审如实标记局限。机器检查只做原文/哈希/State/结构，不能用词命中率替代质量。

**重复读取或不同合法只读工具路径不直接扣任务合格；计入成本和效率。** 错误宣称与事实矛盾单列；final_answer仅为提交。工具读取组未真正获得文件却提交回答，其证据获取是否符合“阅读指定文件”的约束单独核对，不能用事先知道的事实伪装读过。

### 两组如何共用唯一输入构造

- 直供组接收原样完整文件作为**用户提供的资料**，不是参考总结、要点或伪造工具返回；程序只原样读取已冻结文件来构造诊断资料，不提炼答案。
- 工具组只接收相同任务及文件路径，由RWKV生成实际读取调用，Harness将真实观察沿原State注入，再由RWKV自己决定作答。
- 当前 `create_literal_goal(request, workspace_root, constraints, runtime_policy)` 没有独立附件参数。最小无生产改动方案是直供组在共同任务文本后追加有来源边界的原文件资料，仍调用同一create_literal_goal/_assignment/render_bootstrap。分别保存共同任务句子的SHA与实际完整request的SHA：二者的实际request及goal digest必然不同，不能声称逐字相同。资料边界文案也在运行前冻结，不能隐含“必须直接final”或注入评分。
- 如需产品通用附件入口，另做生产唯一builder扩展及red→green后重新冻结两臂，不能在temp手写第二套协议，也不能向direct组假注一次成功read_file。
- 两组保留相同可用工具和只读任务约束，不在direct组强制只准final，也不在tool组指定首个调用。direct组若自行再次读取，按分配组保留结果并标“发生重新读取”，单列轨迹，不删除/替换它来改善差距。偶发目录查看不等于本轮升级搜索任务；不布置新定位任务。

### 看什么、怎样解释

主结果按匿名语义尺度逐题配对，报告满足/部分/不满足/无结果、事实问题与重要遗漏；报告实际获取全文与State证据。读调用合法率、额外调用、token等是解释项。成本/延迟两臂都记，但直供省了真实工具工作，不能直接宣称生产方案成本收益。

两遍全部“满足”、无无依据陈述与工程不变量失败，可称该组固定样本内稳定；这是推进门，不是将所有其他质量梯度折成“不会总结”。原读取回归保持独立报告；生产改动时全组重跑，不能把原R1/R2与新评分合并。

预先约定结论方向：

1. 两组接近且较好：无必要根据当前四文件增加架构补偿，保持简单。
2. 直供较好、工具较差：先检查原始输入、获取完整性和恢复模式；确实无机械问题后，才分别对照输入元数据/菜单或历史封装。
3. 两组都不足：检查合理口径下的摘要能力、目标表达及两组共有的19工具菜单/Agent指令负担；不能仅据此归咎工具观察链，也不能排除共同封装影响或直接归因于模型能力。必要时另轮登记纯文本摘要参照，固定全文、任务、模型、采样及评分，明确其协议差异；该参照只作诊断，不替代生产输入协议或作为生产成本收益。
4. 少量差异或遍次方向相反：报告不确定，不选赢家；下一轮事前确定更多重复或新获准覆盖，不在本轮边看边追加。
5. 真正State/观察/工具缺陷：单独保留失败证据，工程回归先红后绿，再新冻结；不修改parser/评分/stop后重算本轮。

仅4文件×2遍的差距不证明统计显著或普遍稳定。差异可能同时来自全文位置、上下文长度、观察格式、前序调用和State历史；后续每轮才隔离一个因素。

## 后续优先级与启动条件

| 优先级 | 新增问题 | 必须先具备的证据 | 最小验证方向 |
|---|---|---|---|
| P2 | P1指向的单一缺陷/输入因素 | 可复核失败或明确差距，不凭猜测 | 只改一个点；或故障注入核验cache重建/观察，原读取回归不退化 |
| P3 | 自主定位文件 | 当前单文件结果口径可用、已有闭环证据 | 不给准确路径，评价最终找到内容及回答；定位与理解分别归因 |
| P4 | 单处修改 | 能定位/理解目标、真实工具执行可信 | 外部对文件行为验收，不限定write/patch路径；保留错误修改 |
| P5 | 修改与测试反馈 | 单处修改可用 | RWKV执行公开测试、利用真实失败修复；不能伪报测试通过 |
| P6 | 多文件依赖和集成 | 局部变更与反馈闭环可信 | 先串行小任务、最终集成行为验收，验证依赖版本与冲突，不立即并发 |
| P7 | 强模型是否补足明确困难 | 当前任务有RWKV基线和可复现困难；交接、权限及预算规则已冻结，不要求P6通过 | 先建议后继续，再单独测试接管；共享预算、贡献与成本分开 |
| P8 | 并发能否提高合格吞吐/降低交付时间 | 独立只读任务：合格基线及State隔离可靠；并行修改另需写隔离证据，同项目修改还需冲突/集成证据 | 独立只读任务→独立修改→可证明独立的同项目工作；逐档负载、同质量比较 |

这些编号是工作项标识，不是必须逐项全通过的串行门。先完成P0/P1；之后有可复现困难即可启动P7，独立只读任务满足隔离与质量条件即可启动P8，均不等待P6。多文件协作、同项目并行写入仍按其真实依赖推进。可提前准备各项离线工程验证，但真实实验分别登记，避免共用推理服务造成相互干扰。

P7首先冻结显式求助、客观错误/资源事件、等待写权限、接管执行者和交还State的约定，检验帮助是否有效，而非要求RWKV先独立解决该困难。P8先比较同批独立只读任务串行/并发的质量与实测资源，再扩大范围。长任务交接另设定位轮次，明确新State与原State延续的区别，不把摘要压缩或上下文重建当作已验证能力。

未来每个实际项目仍由目标与依赖决定任务数与步骤；这些验证不恢复六角色流水线，也不授权当前立即启动推理实验。

## 每项代码变化的共同门

完整失败轨迹和来源 → 新行为回归先失败 → 最小修复 → 相关/全量测试按仓库规范通过 → 冻结代码/协议/任务/模型/State/采样/预算/评分 → 新的真实运行 → 结果、成本与失败候选完整封存 → 本地提交。既有未提交修改先核对SHA，不能被恢复基线脚本覆盖。旧实验按旧口径保留；没有数据构建或训练授权就不启动这些通道。
