## 2. 必须长期保持的设计前提

RWKV 在本项目中按状态驱动的续写模型使用。下一段生成取决于当前模型 State 与新增输入；Harness 返回工具结果后，宿主程序中的 while 循环本身不会变成模型可见的任务指令。

因此每次决策必须有明确、可检查的当前任务、阶段、最新事实、未完成工作、可选决策及输出边界。持续 State 用于保留当前工作单元的上下文；持久任务记录保存显式计划、真实证据和责任归属。不能把递归 State 当作可直接读取、必然精确的业务进度表，也不能假设追加一句提醒就能保证任务能力。

需要区分三个状态：训练得到的初始 State profile、任务运行中累积的 Native State、程序持久化的计划与执行状态。训练初始 State 不等于运行进度；状态哈希一致不等于目标已完成；重建成功不等于每条历史信息都被模型有效使用。

本轮更正先前口头判断：初始 _assignment 已明确要求“Choose one direct operation to make progress”；不能声称完全没有任务推进要求。缺口在于后续决策缺少显式、动态的计划/进度闭环，以及普通反馈仅重新打开 JSON 续写位置。

## 3. 已确认的主要问题

### A1 / P1：实际入口绕过已有计划链，文档与路由不一致

rwkv-lh → scripts.run_rwkv_agent → CodingJob → read_only_agent._run_job → LongHorizonController。direct_agent_settings 强制 native_required、full 工具披露。Web worker 也走 CodingJob；旧 product_runtime.build_product_controller 中 Strong Planner＋StatefulGoalLoopController 的多角色路径不在该直接入口中。

docs/ARCHITECTURE 说明直接链；G1J 规范虽已在页首指向现行导航，后续段落仍写 CLI/Web 统一进入 StatefulGoalLoopController。代码中旧 contract graph、parallel atoms、online supervisor、五角色链和直接链同时存在，研究测试通过不代表 CLI 实际使用这些能力。

影响：使用者以为启用了 Planner/阶段审核，真实项目却只进入全目标工具循环；研究数据和生产数据也可能被混淆。需要统一生产工厂、运行时架构证明、CLI/Web/采集/评测路由测试；退役入口按仓库规则清理，不直接恢复旧模式。

### A2 / P1：没有模型可见的局部计划与结果驱动更新阶段

初始输入有原始需求、工具、工作区摘要和一般推进指令。每次有效生成被提交、Harness 执行后，普通观察由 render_event_append 渲染为 Function output，再接 Assistant JSON opener。直接链没有 RWKV plan/progress/help/subtask_done 的独立合法决策。

R38 初次生成实际包含 analysis、plan 和 commands/keystrokes，并开始写长代码，随后 length；它同时违反单工具协议和长度边界，整个候选被拒绝/回滚。这个事实支持“模型产生了规划内容，但接口未提供可执行规划通道”，不能证明这份计划正确，也不能直接执行其不完整代码。

影响包括读后不修改、写后不验证、错误后不调整、已完成局部工作后继续重复。新增计划必须参与后续决策，不只是开头的一段装饰性文本。

### A3 / P1：强模型已接入，但常用建议接口不承担规划

当前 advice 模板源于摘要二次意见，ADVICE_SYSTEM 明文禁止 plan、工具参数和替代答案；调用传入 goal、空 files、原 final、动作观察，不包含被拒绝的原始生成和完整阶段诊断。

R39 强模型不知道 R38 那段被拒绝的计划/代码；其回答仍围绕“没有候选摘要可审核”，并错报读取次数。建议事件确实进入后续输入，但 3 次继续均列目录。不能把这一结果称为“强模型规划后仍无效”。

GoalJob 的 on_stall=takeover 支持终止后的有限接管，属于产品能力；普通单任务不自动启用。Web 当前还显式拒绝 resume。离线 DeepSeek 纠错也不是在线 Planner。必须在同一任务流程中明确区分规划、诊断建议、接管和离线教师。

### A4 / P1：直接模式的提交标记没有目标完成证明

_run_job 使用 min_actions=0。无额外执行合同时，合法 final_answer 可以直接设置内部 completed，acceptance 仍是 not_evaluated。离线脚本化探针在“修改工作区”任务中只返回一句完成声明，0 动作、0 文件仍得到 completed。

这是现有 submission 语义，不是声称真实 RWKV 在本轮作了虚假声明。若产品按 completed 认定实现完成，则属于严重语义缺口。应区分子任务报告、整体完成候选和已验证交付；RWKV 结合目标覆盖与执行证据提出完成，公共完成检查及必要任务级 review 决定交付状态。隐藏验收保持隔离。

### A5 / P1：存在已复现的取消异常被工具边界吞掉的问题

LongHorizonController._execute_decision_locked 捕获 BaseException，仅特殊放行 rwkv_lh_process_loss。job_budget.WallDeadlineExpired 正是 BaseException 子类，但不具有此标记。

离线注入同一取消异常后，它被转换为普通工具失败，Controller 又调用脚本化模型并到达 completed。原异常定义明确写着不应被可恢复模型/协议处理吞掉。跨所有 Harness 动作有效，可能使超时/取消之后仍进行额外处理。

限制：真实 outer job 还有 elapsed 时间与生成预算检查，不能因此断言实际任务一定超预算无限运行。本轮证明的是内部取消传播与错误分类缺陷。应先加失败回归，再修通用取消传播，确保已开始动作的副作用证据可恢复。证据 OFFLINE_FAILURE_PROBES.json；未修改生产代码。

### A6 / P1：错误恢复只有格式反馈，缺少可执行的任务恢复决策

非法输出回滚到父 State 后主要回注错误、拒绝参数和相关 schema。R38 那段非调用计划的内容未进入有效执行链，也没有递交强模型做阶段诊断。合法化不等于推进：R39 无新协议拒绝仍停滞。

R40 timebook-add 已写文件，随后五次相同命令均 exit 2，错误明确指出 CLI 参数不支持，却没有修改命令或实现。错误反馈应同时说明“上一步结果、当前未完成目标、下一次需作何种决策”；完整拒绝输出留审计，向诊断方提供必要原文。不能自动补业务参数或执行被拒绝候选。

### A7 / P2：模型输入负担与续写边界值得优先验证

结果保留完整审计身份是优点，但现在模型侧也收到大量 SHA、投影元数据和工作区摘要。R38 TASK.md 实际仅 3517 字节，读后输入从 5318 增至 8131、10956 token；R40 query 源增长至 26259 逻辑 token。这是观察、动作与元数据累计，不等于 State 发生了截断。

精确重放还可见生成停止于 User 标记后，追加器再次写 User: Function output，形成重复角色边界。STATE_FEEDBACK_AUDIT 逐生成登记出现次数。记录与真实 tokens 相符，尚未证明其造成质量下降；应在当前模型的完整会话模板/stop 合同中验证。不能只改 stop 再对旧 confirmation 重评分。

建议模型侧保留简洁的事实内容、错误、完整性、必要引用和读取游标；完整 SHA 链留审计侧。投影缺失必须显式可见，模型可以取回缺失内容。不能通过摘要删掉未完成计划或关键证据。

### A8 / P1（上线前）：State 生命周期设计尚未对应语义工作单元

当前直接链一般整个目标一个 Native lane，靠真实增量持续推进。未提交的 start_atomic_actor_state / online supervisor 改动试图按微任务启动新 State，但它们不在当前 CLI 的默认路由，不能算已上线能力。

建议同一语义子任务内保留连续 State，跨独立子任务可新建 State，但必须显式携带原目标约束、相关真实事实、局部计划和工作区版本。不得每个工具调用重置，也不得假设换 State 能消除所有循环。必需事实超预算时应拆分获取或明确中断，不静默截断。重放通过与数值兼容探针继续保留，两者各自证明有限范围。

### A9 / P1（训练前）：局部纠正数据不能替代连续推进能力验证

当前教师目标明确是原真实输入上的一个 function/params。learning_contract 用于离线生成/审计，R39 报告明确它不进入生产提示。两条分别独立验证的纠正不能拼成从未实际发生的连续成功轨迹。

数据链已有精确重建、来源隔离、执行证明和格式门，应保留。但若生产新增计划/进度/求助决策，必须同步唯一 builder、采集、目标监督和评测；旧单动作数据不能自动证明新协议兼容。需要覆盖正常推进、有效失败诊断、修改后验证、失败后修正、完成与求助；正确局部样本数量不能代替端到端验收。

历史 1000 候选被降级待审，未成为新的合格模型；本轮不恢复旧数据/State，不启动训练。计划动作也须来源于真实生产边界，不能伪造计划后工具结果。

### A10 / P2：存储与并发开销可能抵消 Native 增量优势

store.save 每次序列化当前完整因果状态并保留 checkpoint；CodingJob 对每个修改动作复制完整工作区 before/after。真实 Native 推理可以增量，整个产品的日志、快照和磁盘工作仍会随历史及项目规模增加。

这是静态确认的开销来源，未测出本轮时延占比，不认定为当前首要停滞根因。应在正确性稳定后测每个合格任务的总时延/存储/成本，考虑不可变内容引用和可验证增量快照。共享副本冲突需要保守处理；文件不冲突也不证明语义集成成功。

## 5. 建议的一条统一架构

产品目标：RWKV 作为持续状态的主要执行模型；强模型提供任务级规划与困难处置；工程层保存事实、执行明确动作、控制资源。简单任务与复杂任务使用同一闭环，区别在计划规模与强协助配置。

复杂项目建议：强模型先提出结果导向的整体计划和依赖；简单任务可由 RWKV 提出单项或短计划。不能用路径/题型特判决定计划内容。原目标保持不可变，规划假设可被执行证据修正。计划规模由任务需要决定，不设固定步数上限，也不将固定阶段数量变成隐性上限。

每个语义工作单元按以下顺序运行：

1. 明确当前子目标、依赖结果、验证方式和限制，建立/恢复对应 RWKV State。
2. RWKV 生成可持久化的局部计划；简单子任务可以只有一项。计划输出是合法协议决策，不当作工具执行。
3. RWKV 选择工具及参数，Harness 实际执行；一次合法动作只是执行事实。
4. 将真实结果和当前显式任务状态追加到同一 State，并明确要求核对结果、更新计划进度、选择下一步。
5. 下一次生成可以提交简短进度判断及一个动作，也可以请求帮助、报告子任务完成或提出全局完成候选。不要求输出冗长思维过程；判断可与下一动作在同一次生成里表达，避免每个工具必添一次独立模型调用。
6. 工具失败通常先在当前子任务修正。RWKV 明确求助、依赖矛盾、阶段集成失败或预注册停滞边界时，调用强模型诊断/调整计划；必要时允许接管。总预算不重置。
7. 子任务完成报告引用真实证据；更新全局计划，调度下一依赖就绪子任务。独立工作单元可以并发，写入冲突和语义集成单独验证。
8. RWKV 结合原始目标、计划覆盖和执行证据生成最终候选；执行公共完成检查，复杂项目可进行强模型任务级交付复核。问题以具体缺口返回闭环；预算用尽就是中断。强模型如果修改/接管最终产出必须保留来源，Controller 不重写业务回答。

每次观察后的模型可见要求至少包含：当前局部目标、上一步事实与错误、尚未完成事项、可用帮助/结束选项、期望的下一决策格式。示意自然语言如下（不是新的可执行协议或已上线提示）：

> 上一步的真实结果如下。请结合当前子目标和计划，判断它解决了什么、还缺什么；更新必要进度，并选择一个能推进任务的下一动作。若缺少信息，获取缺少的证据；若遇到无法处理的问题，明确求助；若子目标完成，引用证据报告完成。不要把建议、命令成功或未经验证的猜测当作整个任务已完成。

这与“把完整原目标再重复一次”不同：需要真实、动态的局部计划和反馈闭环，不能仅靠话术宣称收益。

强模型职责边界：可以规划、诊断、调整任务粒度、综合、必要时接管；不成为所有工具前后的强制串行审核。RWKV 保留本地计划、工具选择、修改和验证能力，不能退化为只填强模型参数。计划与建议永远不是已执行事实。

## 6. 实施顺序与可证伪验证
